# Evaluation Plan

## 1. Evaluation objective

Determine whether the system can reproduce known controlled failures and whether its diagnosis adds value beyond repeated reruns and deterministic rules.

## 2. Benchmark design

Build a local demo application with a known injected cause for each scenario. Start with 5–10 scenarios and increase the set only when each scenario has a documented, testable ground truth.

Initial scenario ideas:
- Delayed UI state / synchronization.
- Delayed or failed local API response.
- Overlay blocks an intended interaction.
- Stale or missing test data.
- A non-flaky deterministic failure as a negative control.

For each scenario, document:
- Cause injected.
- Steps to reset the environment.
- Expected observations.
- Expected failure signature.
- Conditions that count as matching.
- Known confounders.
- Number of repeated trials.

## 3. Baselines

Compare the agent with:
1. **Single rerun baseline:** rerun the test once without diagnosis.
2. **Repeated rerun baseline:** rerun up to the same attempt budget.
3. **Deterministic rules baseline:** classify using structured signals without an LLM.
4. **AI-assisted version:** same experiment budget with hypothesis generation and bounded selection.

Keep attempt/time budgets comparable. Do not compare an agent with ten attempts to a baseline with one attempt without reporting that difference.

## 4. Metrics

### Reproduction rate
For cases designed to be reproducible, fraction of investigations where the system recreates the target failure according to predefined matching rules.

### Diagnosis accuracy
Fraction of cases where the selected cause matches the known injected cause. Report per-category and overall results.

### False diagnosis rate
Fraction of cases where the system asserts a cause that is not supported by the ground truth/evidence.

### Inconclusive rate
Fraction of investigations correctly left unresolved because the evidence or outcome is insufficient. Also measure incorrect confident conclusions separately.

### Experiment efficiency
Number of runs and elapsed time until a valid outcome, compared with baselines.

### Outcome classification
Accuracy distinguishing matching reproduction, passing run, unrelated failure, timeout, and insufficient evidence.

## 5. Reporting rules

- Report the number of scenarios and trials.
- Report the exact matching criteria.
- Keep failed and inconclusive attempts in the results.
- Do not report a target percentage until baseline measurements exist.
- Do not tune and evaluate on the same hidden scenarios without noting the limitation.
- Publish aggregate results and reproducible commands.
- Label all sample reports as illustrative unless generated by an actual run.

## 6. MVP acceptance criteria

The MVP is acceptable when:
- The benchmark runs locally without a paid API.
- Every outcome includes its comparison rule and supporting evidence.
- The system distinguishes unrelated failures from reproduced failures.
- A human can rerun the benchmark from the repository instructions.
- Results include limitations and a comparison against at least one baseline.

## 7. Limitations to disclose

Controlled injected failures are easier than arbitrary real-world failures. Results from a small synthetic benchmark cannot establish general production accuracy. Reproduction may fail because of nondeterminism, missing artifacts, environment differences, or a rare trigger. An inconclusive result is preferable to an unsupported root-cause claim.
